## 一、核心结论

1. **文档是最常用的攻击投递载体**：钓鱼附件 → 用户点开 → 宏/嵌入动作执行 → 二阶段载荷落地。签名引擎（ClamAV/YARA）对定制化恶意文档天然滞后，**结构语义检测**（"正常业务文档不应该长这样"）是不依赖情报更新的补充防线。
2. Office 格式分两代：**OLE2 复合文档**（.doc/.xls/.ppt，1997-2003，二进制容器）与 **OOXML**（.docx/.xlsx/.pptx，2007+，ZIP 套 XML）。宏都存放在 `vbaProject.bin`，两代格式中位置不同 —— 检测方式也不同（OOXML 看条目名，OLE2 用 POI 真实解压提取宏源码）。
3. PDF 的危险在**动作对象**：`/OpenAction`（打开即执行）、`/JavaScript`、`/Launch`（执行外部程序）、`/EmbeddedFile`（夹带载荷）。
4. 本项目的检测分两级哲学：**浅检测**（流式/分块、O(1) 内存、只看明文层）+ **签名引擎兜底**（压缩层交给 ClamAV/YARA）；对宏的处置分 **BLOCK（隔离）/ FLAG（放行打标）** 两档，因为良性宏在业务中真实存在，而 ActiveX/PDF 危险动作几乎不存在正常场景。

## 二、威胁模型：为什么文档是头号攻击载体

邮件/IM 传文件天然绕过边界防护，收件人又天然信任"看起来正常"的文档。典型攻击链（对应 MITRE ATT&CK）：

```
钓鱼邮件携带恶意附件                    T1566.001（鱼叉钓鱼附件）
        │ 用户打开 docx，看到黄色提示条"启用内容"
        ▼
用户点击启用 → 宏自动执行                 T1204.002（用户执行：恶意文件）
        │ AutoOpen / Document_Open 触发
        ▼
宏调用 Shell / PowerShell 从外部下载载荷
        ▼
二阶段植入：远控、勒索、凭据窃取           T1071 等命令控制
```

这条链上每一环都是"正常功能"：宏本就是 Office 的合法自动化能力，`Shell()` 是合法 API —— 所以**内容级恶意检测不能只看"有没有宏"，要看"宏里在干什么"**，这正是本项目 OLE2 检测提取真实宏源码、按可疑 API 判定（而非见宏就杀）的原因。

## 三、Office 文件格式两代史：OLE2 与 OOXML

| | OLE2 / CFB | OOXML |
|---|---|---|
| 扩展名 | .doc / .xls / .ppt（97-2003） | .docx / .xlsx / .pptx（2007+，ECMA-376） |
| 本质 | 复合二进制文档：类文件系统的扇区存储 | **ZIP 容器 + XML 部件（parts）** |
| 文件头 | `D0 CF 11 E0 A1 B1 1A E1` | `50 4B 03 04`（PK） |
| 内部结构 | Storage（目录）/ Stream（文件）层次，FAT 扇区表 | `[Content_Types].xml` + `_rels/*.rels` 关系 + 各 XML 部件 |
| 宏位置 | `VBA` Storage 下的流（整体称 vbaProject） | `word/vbaProject.bin`、`xl/vbaProject.bin` 等 ZIP 条目 |
| Java 解析 | POI POIFS（本项目 `VBAMacroReader`） | `java.util.zip.ZipFile` / commons-compress |

**关键认知：OOXML 文档就是 zip**。解开一个 docx 看一眼，所有"结构检测"立刻具象化：

```
$ unzip -l 正常的.docx
[Content_Types].xml          ← 类型声明表
_rels/.rels                  ← 关系（哪个是主文档）
word/document.xml            ← 正文
word/theme/theme1.xml
docProps/core.xml

$ unzip -l 带宏的文档（本应是 .docm/.xlsm）
word/document.xml
word/vbaProject.bin          ← 宏代码（压缩存储）
word/vbaData.xml
```

由此得到一条硬规则：**.docx/.xlsx/.pptx 是"无宏格式"，出现 `vbaProject.bin` 必属异常**（要么是改名的 .docm，要么是手工构造的伪装）—— `DocumentThreatScanner.scanOoxml` 据此判定，不需要读宏内容。

OLE2 那边正相反：.doc/.xls **本来就支持宏**，正常业务（财务模型、报表工具）可能带良性宏 —— 所以 OLE2 检测必须解开宏看内容（见下节），而不是条目级一刀切。

## 四、VBA 宏：机制、攻击链与检测

### 4.1 自动执行锚点与危险 API

VBA（Visual Basic for Applications）是嵌在 Office 文档里的脚本。恶意宏的固定套路：

```vb
Sub AutoOpen()                                    ' ← 自动执行锚点：文档打开即触发
    ' 同类锚点：AutoExec / Document_Open / Workbook_Open / Auto_Close
    CreateObject("WScript.Shell").Run "powershell -nop -w hidden -c IEX(...)", 0
    ' ↑ 危险 API：Shell( / CreateObject / WScript.Shell / cmd.exe / powershell
    '   URLDownloadToFile —— 下载二阶段载荷
End Sub
```

`DocumentThreatScanner.SUSPICIOUS_MACRO_TOKENS` 就是这两组锚点的清单：`autoopen, autoexec, document_open, workbook_open, shell, wscript.shell, cmd.exe, powershell, urldownloadtofile, createobject`。**自动执行锚点 + 危险 API 组合出现才判威胁**，只含普通业务逻辑（数据处理、格式设置）的宏放行 —— 与 YARA 规则 `Suspicious_Office_Macro` 的三段式条件思路一致。

### 4.2 为什么必须用 POI 真实提取（而不是字节扫描）

宏源码在 `vbaProject.bin` 内部按 **MS-OVBA 规范压缩存储**（基于 LZ77 变体的自定义压缩算法），直接对文件做字节级搜索 `AutoOpen` 大概率搜不到 —— 这也解释了 YARA 规则为什么对很多真实恶意文档"看得到容器看不到内容"。Apache POI 的 `VBAMacroReader` 完整实现了 MS-OVBA 解压：

```java
try (VBAMacroReader reader = new VBAMacroReader(file.toFile())) {
    Map<String, String> macros = reader.readMacros();   // 模块名 → 反解压后的源码
    // 拼接所有模块源码，逐个 token 匹配 SUSPICIOUS_MACRO_TOKENS
}
```

- 返回 `Map<模块名, 源码>`，源码是明文 VBA 文本，token 匹配可靠；
- `IllegalArgumentException` 表示"不是 OLE2 文件"（伪装场景已被 Tika 拦截，这里是双保险），按非文档处理返回 null。

## 五、ActiveX 与其他嵌入风险

ActiveX 是 Windows COM 控件，可嵌入 Office 文档（OOXML 中位于 `word/activeX/`、`xl/activeX/` 目录，含 `.bin` 控件序列化数据）。风险：

- 历史上大量 IE/Office ActiveX 控件存在 RCE 漏洞，文档只需诱导目标打开即可触发控件加载；
- 相比宏，**正常办公文档几乎不存在嵌入 ActiveX 的理由** —— 因此 `DocumentThreatScanner` 对它不做策略分级，`macro-policy=FLAG` 也不豁免，命中即 `INFECTED`（Kind.ACTIVE_X）；
- 实现上 **ActiveX 先于 VBA 判定**（`scanOoxml` 的检查顺序）：两者并存的文档若 VBA 先命中，FLAG 策略会将其放行打标，"ActiveX 始终拦截"就被绕过了 —— 先判 ActiveX 保证高信度信号不受宏策略影响。

同族的其他向量（本项目未检测，属扩展方向）：

| 向量 | 说明 |
|---|---|
| DDE 公式注入 | Excel 单元格 `=DDE|...` / `=CMD|' /c calc'!A0`，无需宏即可执行命令 |
| OLE 嵌入对象 | 文档内嵌打包的可执行对象（packager.exe 载体） |
| 外部链接 / 远程模板 | `word/_rels/document.xml.rels` 指向远程 DOTM，打开时拉取恶意模板（远程模板攻击） |
| Office 加密容器 | 加密 Office 文件任何扫描都失效，应在预检层直接拒绝 |

## 六、PDF 结构与危险动作

### 6.1 PDF 对象模型一分钟入门

PDF 是文本与二进制混合的容器，由带编号的对象构成：

```
%PDF-1.7                                    ← 头（Tika/YARA 魔数锚点）
1 0 obj
<< /Type /Catalog /Pages 2 0 R /OpenAction 3 0 R >>      ← 文档根（Catalog）
endobj
3 0 obj
<< /S /JavaScript /JS (app.alert\(1\)) >>                ← 动作对象：打开即执行 JS
endobj
...
xref                                        ← 交叉引用表（对象偏移索引）
trailer << /Root 1 0 R /Size 20 >>
startxref
1234
%%EOF                                       ← 尾
```

`<< ... >>` 是字典（键值对），`/JS (…)` 里的圆括号是字符串。理解到"对象 = 编号 + 字典"即可看懂威胁特征。

### 6.2 危险动作字典

| 关键字 | 危险性 | 说明 |
|---|---|---|
| `/OpenAction` + `/JavaScript` | 高 | 打开文档**自动执行** JS —— 无需用户交互，钓鱼首选。`/JS` 可内联字符串也可引用流对象 |
| `/AA`（Additional Actions） | 高 | 各生命周期事件（打开页面、关闭、鼠标）挂接的动作，`/OpenAction` 的兄弟 |
| `/Launch` | 高 | 执行外部程序（历史案例：诱导用户"此文档需用其他程序打开"执行 cmd）。现代阅读器已拦截/警告，但仍是强恶意指标 —— `DocumentThreatScanner.scanPdf` 命中即报 |
| `/EmbeddedFile` / `/FileAttachment` | 中 | 夹带任意文件（恶意 exe/lnk 的常见藏身处） |
| `/URI` / `/GoToR` | 低 | 跳转链接/远程文档，钓鱼配套 |
| `/RichMedia` | 低 | Flash 时代漏洞载体，随 Flash 淘汰基本绝迹 |

本项目 `scanPdf` 的判定组合与业界工具（如 Didier Stevens 的 pdfid.py）同源：`/JavaScript` **且** `/OpenAction` 同时存在 → 自动执行的 JS；`/Launch` 单独存在即威胁。

## 七、浅检测 vs 深检测：分块扫描与压缩盲区

### 7.1 本项目的浅检测实现

`scanPdf` 不加载整个文件，而是 **1MB 分块 + 64B 重叠窗口** 扫描关键字：

```
文件字节流:  [.....chunk1 (1MB).....][overlap 64B][.....chunk2.....][overlap]...
                  │                        │
                  └── 本块扫描 ─────────────┘── 尾部 64 字节移到下块开头
                        防止 "/OpenAct" + "ion" 这类关键字恰好跨块被漏检
```

两个实现细节的"为什么"：

- **重叠 64 字节**：最长关键字 `/javascript` 只有 11 字节，64 留足余量；
- **ISO-8859-1 解码**：Latin-1 字节↔字符 1:1 双射，解码永不吞字节、永不抛异常（用 UTF-8 解码多字节序列可能把合法 ASCII 误折叠、非法序列直接炸）。

内存恒定 O(1)：100MB 的 PDF 也只占 1MB 缓冲 —— 这是对应测试用例"100MB 大 PDF → 扫描内存占用平稳"要守护的性质。

### 7.2 已知盲区：压缩对象流

PDF 允许把多个对象打进 **ObjStm（对象流）** 并 FlateDecode（zlib）压缩 —— `/JavaScript`、`/OpenAction` 等关键字在压缩层里是二进制，明文扫描与 YARA 规则**同样看不到**（两者盲区一致，属已知限制）：

- 深度方案是规范级解析：PDFBox（`org.apache.pdfbox`）解析对象树后动作字典全可见，代价是全量加载 + 解析器自身的 CVE 风险面；
- 本方案的取舍：**浅检测保吞吐与内存，压缩层交给 ClamAV**（clamav 引擎自带 PDF 解析器，会解压 ObjStm 提取 JS 分析）+ 病毒签名兜底。
- 若未来要加强，优先级建议：先扩 YARA（如 `pdfid` 风格的 `/ObjStm` 计数规则），再考虑引入 PDFBox 深解析。

## 八、ZIP 炸弹与四维流式防护

### 8.1 问题本质

压缩比可以任意高：100KB 的 zip 可能解压出 100GB（重复数据极度可压缩）。若服务端扫描时顺手解压/解析，一个上传请求就能耗尽磁盘或内存 —— 这是 **DoS 向量**，与文件是否"有毒"无关，必须在解压前/解压中设限。著名样本 `42.zip`：嵌套解压可膨胀到 PB 级。

### 8.2 四维流式防护（`FileTypeValidator.inspectZip` 实现）

| 维度 | 配置项（默认值） | 防什么 |
|---|---|---|
| 条目总数 | `max-entries: 10000` | 海量空 entry：光是遍历目录就能拖垮服务 |
| 单 entry 解压大小 | `max-entry-uncompressed: 100MB` | 单个巨型文件 |
| 累计解压总量 | `max-total-uncompressed: 1GB` | 千层小文件累加 |
| 压缩比 | `max-compression-ratio: 100` | 异常压缩比（正常文档很少超 10:1） |

**嵌套 zip（zip-in-zip，42.zip 结构）不做递归展开**：递归解压嵌套包，这个动作本身就是攻击者想要的 CPU/内存消耗（你得先解开它才能测量它）。实现选择是不展开 —— 内层 `.zip` 条目的数据照常计入累计总量与压缩比预算（爆炸规模仍有硬上限），嵌套内容的威胁检测由 ClamAV/YARA 对原始字节扫描兜底。

实现要点：

- **流式**：`ZipArchiveInputStream` 顺序读（不加载 central directory、不落盘解压），超限**即时中断**返回拒绝原因；
- **不信任 header 声明值**：本地文件头的解压大小由压缩包作者完全可控（谎报小 size 即可绕过按声明值累加的检查），因此**所有 entry 一律实际解压、边读边计数**，单 entry 与累计两个上限在读取循环里逐块校验；声明值与实际不符会导致流错位、后续 header 解析失败 —— 同样被 fail-closed 拒绝。这是流式 zip 处理的经典细节；
- **不递归**：内层 `.zip` 条目不展开检查（理由见上），其数据量仍计入预算。

### 8.3 为什么放在 Tika 阶段而不是独立阶段

zip 炸弹是**结构 DoS**，越早拦截越省后续所有引擎的功 —— ClamAV/YARA/文档检测都要读文件，先在类型校验阶段把炸弹挡掉，后面阶段的资源消耗才是有界的。OOXML 检测用 `ZipFile` 列条目名之所以安全，是因为此时文件已通过解压炸弹检查。

## 九、在本项目中：分级处置哲学

`DocumentThreatScanner` 返回的 `DocThreat` 带 `Kind`（MACRO / ACTIVE_X / PDF_ACTION），`VirusScanService` 据此分级：

```
Kind.MACRO（VBA 宏）
  ├─ macro-policy = BLOCK（默认）→ INFECTED，进隔离区
  └─ macro-policy = FLAG         → 放行，CLEAN + threat="macro-flagged: ..."
                                    （业务存在良性宏时的可配置逃生舱）

Kind.ACTIVE_X / PDF_ACTION
  └─ 永远 INFECTED —— 正常业务文档没有嵌入 ActiveX、
     自动执行 JS、/Launch 的理由，不设豁免
```

设计依据（`VirusScanProperties` 注释原文的展开）：

- **宏是"低信度信号"**：恶意宏真实存在，但财务报表里的良性宏同样真实。一刀切隔离可能砍掉业务，全放行则防线失效 → 策略化，让安全负责人按业务实情选；
- **ActiveX/PDF 动作是"高信度信号"**：几乎没有正常场景，不需要策略；
- FLAG 打标（`macro-flagged: ...` / `scan-engine-degraded`）会贯穿 `ScanResult.threat` 一路透传到 API 响应 —— "放行但可见"，而不是静默放水。

另注意检测顺序的设计：文档威胁检测在管道**第四站**（ClamAV/YARA 之后），且只对 `isDocumentFormat(mime)` 的文件执行 —— 签名引擎先行可以少做功（命中即短路），Tika 的 mime 复用则避免二次探测。

## 十、动手实验：构造测试样本

以下样本全部无害，仅用于触发检测逻辑。

### 10.1 伪装宏文档（OOXML → Kind.MACRO）

```bash
mkdir t && cd t
# 解开一个正常 docx，塞入假宏条目，重新打包
unzip ../任意.docx > /dev/null
echo "fake" > word/vbaProject.bin
zip -r ../fake-macro.docx . > /dev/null
cd ..

mvn spring-boot:run
curl -F "file=@fake-macro.docx" http://localhost:8080/api/files/upload
# 默认 BLOCK → 422 "Office 文档包含 VBA 宏"
# 配置 zxf.virus-scan.macro-policy=FLAG 后 → 200 且 message 含 macro-flagged
```

### 10.2 恶意 PDF（Kind.PDF_ACTION）

```bash
cat > evil.pdf <<'EOF'
%PDF-1.4
1 0 obj << /Type /Catalog /OpenAction 2 0 R >> endobj
2 0 obj << /S /JavaScript /JS (app.alert\(1\)) >> endobj
trailer << /Root 1 0 R >>
%%EOF
EOF

curl -F "file=@evil.pdf" http://localhost:8080/api/files/upload
# 期望 422 "PDF 包含自动执行的 JavaScript"
```

### 10.3 ZIP 炸弹（触发解压炸弹检查）

```bash
# 高压缩比样本：50MB 零字节压成 ~50KB
python3 -c "
import zipfile
with zipfile.ZipFile('bomb.zip','w',zipfile.ZIP_DEFLATED) as z:
    z.writestr('a', b'\x00' * (50*1024*1024))
"
curl -F "file=@bomb.zip" http://localhost:8080/api/files/upload
# 50MB/50KB = 压缩比 1000 → 期望 400 "疑似 ZIP 炸弹，压缩比超过 100:1"

# 海量 entry 样本（改 max-entries 验证）
python3 -c "
import zipfile
with zipfile.ZipFile('many.zip','w',zipfile.ZIP_DEFLATED) as z:
    for i in range(20001): z.writestr(f'e{i}', '')
"
```

### 10.4 真实 OLE2 宏（VBAMacroReader 路径）

真实带宏的 .xls 样本需要 POI 或 Office 生成，手工伪造 vbaProject.bin 二进制较难 —— `DocumentThreatScannerTest` 用 POI 生成的**无宏良性 xls** 验证 `VBAMacroReader` 空宏路径不误判（返回 null），恶意宏路径由 OOXML 伪装样本覆盖同一 `Kind.MACRO` 分支。

## 十一、常见坑与最佳实践

| 坑 | 说明 / 对策 |
|---|---|
| 见宏就杀 | 误伤真实业务宏；按"自动执行锚点 + 危险 API"组合判定 + macro-policy 分级（本项目做法） |
| 字节扫描宏源码 | MS-OVBA 压缩存储，明文搜不到；必须真实解压（POI `VBAMacroReader`） |
| 只查 `.zip` 扩展名 | OOXML 全是 zip 容器，压缩炸弹防护必须覆盖 docx/xlsx/pptx；本项目对任何 zip 家族走 `inspectZip`（注意：仅当 Tika 探测为 `application/zip` 时深入，OOXML 探测为具体类型，炸弹检查按当前实现只对 `application/zip` 触发 —— 需要更严时可扩到全部 zip 魔数文件） |
| 信任 header 声明的解压大小 | 声明值由攻击者完全可控，谎报小 size 即可绕过按声明累加的检查；必须一律实际解压边读边计数（本项目实现，声明与实际不符会流错位解析失败 → fail-closed） |
| 解压到临时目录再扫 | 炸弹先落地再检查 = 防护无效；必须流式边读边停 |
| PDF 明文扫描当万能 | ObjStm+FlateDecode 压缩层看不到（已知盲区），文档与 YARA 双写明限制，ClamAV 兜底 |
| 用平台默认字符集解码二进制 | 平台相关且可能抛异常；二进制转字符串扫描用 ISO-8859-1 |
| 大文件全量读入检测 | O(N) 内存；分块 + 重叠窗口保 O(1)（100MB PDF 用例守护此性质） |
