## 一、核心结论

1. **Skill 的输出质量 = 样本 × 约束 × 验证 × 评测的乘积**——这四层是基本盘，任何一层为零，单次输出质量失控；架构层与反馈层是基本盘之上的增强手段（多数 skill 可不用）。只写规则（约束层）是最常见的残缺形态：模型「知道该怎样」却没「见过怎样的」。
2. **评测驱动开发（Eval）是业界公认的第一杠杆**：没有回归比对的规则修改是盲改。改一行规则的效果，只能由「固定输入重跑 + 与金标准 diff」来检验。
3. **回路出口必须显式**：自检清单若无「不通过 → 修复 → 重检」的出口语义，模型可能「核对了、发现了、但照发」。
4. **反例与范例同等重要**：告诉模型「不合格长什么样」和「合格长什么样」是对偶的教学手段，缺前者则失败模式靠猜。
5. 六层方法全景（每层详见对应章节）：

| 层面 | 业界方法 | 一句话本质 |
|------|---------|-----------|
| 样本层 | few-shot 范例 + 反例（negative examples） | 示范的分布覆盖度决定输出的方差 |
| 约束层 | 结构化契约 + 密度配额 + 事实锚定 | 把「写好」翻译成可机械核对的硬约束 |
| 验证层 | 自检清单 → self-refine 回路 | 生成后自评，修订后再输出 |
| Eval 层 | 金标准 + rubric 判分 + 回归重跑 | prompt 工程复用测试工程的全部思想 |
| 架构层 | 多 Agent 信息约束（调查/写作分离） | 写作者拿不到源码就编造不了源码 |
| 反馈层 | human loop（位置选择）+ 生产反馈回写 | 人只进沉淀位与决策位；反例库随真实失败进化 |

## 二、样本层：少样本范例与反例

### 2.1 原理

LLM 对「格式的模仿能力」远强于「格式的服从能力」。同样一条「每卡主路径不超过 10 行」的规则：

- 只写规则：模型理解了，但边界感（10 行怎么算、表格算几行）靠自行发挥；
- 给范例：模型直接对齐范例的密度与形态，规则只负责解释范例为什么这样。

这就是 prompt engineering 的经典结论 **"show, don't tell"**：范例是最高带宽的指令。

### 2.2 关键实践

| 实践 | 说明 |
|------|------|
| **范例覆盖度决定方差** | 范例没覆盖到的任务类型，模型自由发挥——输出方差最大的恰恰是「无范例的类型」。选范例应按任务类型分布（如分布式 / 单体 / 异步受理各一），而非随手找两个 |
| **真实范例优于编造范例** | 从真实代码库调查得来的范例自带「实证密度」；编造的范例会教出编造的输出 |
| **反例（negative examples）** | 每类失败模式配一条「❌ 病理描述 + 正确做法」的反例。反例教的不是格式，是**失败模式的识别** |
| **边界用范例定标** | 规则说不清的边界（多长算空壳、多密算泛滥），用一个正好压线的范例定标，比加规则有效 |

### 2.3 实战对照

`investigate-endpoint-new` 的样本层演进：两份真实开源项目范例（分布式 gRPC 链路 + 单体 CRUD）→ 发现「异步受理形态无范例」→ 补第三份（202 受理 + 轮询）→ 反例从五类扩到六类（补「主线迷失」）。每次扩充的依据都是「输出变形最严重的类型恰好没有范例」这一判断。

## 三、约束层：结构化契约、密度配额与事实锚定

### 3.1 三种约束手段

**① 结构化输出契约（structured output）**：先给输出骨架（章节结构、卡片模板、表格列式），声明「违反即不合格」。骨架把「写好」从开放式问题变成填空题，是最强的质量手段。

**② 密度配额（output constraints）**：对证据与篇幅设硬上限——每卡坐标 ≤ 3 个、代码块 ≤ 5 行、任一事实只出现 1 次。配额的深层价值不是省 token，而是**倒逼排序**：额度不够时模型必须判断什么最重要，这本身就是质量。

**③ 事实锚定（grounded claims / citation）**：要求关键结论必须挂可验证坐标（`文件:行`），且「删掉该证据后结论仍成立则证据不合格」。锚定使输出可审计——读者能沿坐标核对每条结论。

### 3.2 负向指令的局限（高频误区）

「禁止臆造」「不要编数据」这类负向指令效果有限——模型在**无法实证**时仍会硬填。业界做法是给**正向出路**：明确规定「无法实证时怎么办」（如实标注「疑似，未在源码确认」）。给失败一个合法出口，比禁止失败有效。

### 3.3 渐进披露与上下文预算（progressive disclosure）

约束不是越多越好：**常驻上下文的规则量与遵守度成反比**——几十条规则全部平铺在上下文里，每条分到的注意力被稀释，模型对任何一条的执行都变糙。渐进披露是 Agent Skills 架构的核心机制，用分层加载控制进入上下文的规则量：

| 层 | 职责 | 加载时机 |
|---|------|---------|
| SKILL.md（常驻） | 契约：输出骨架、硬约束、原则、参考文件索引 | skill 触发即全文进入上下文 |
| references/*（按需） | 细则：schema 菜单、反例与范例、类型专属模板 | 执行到对应环节才读 |

关键纪律：常驻部分只放「每次执行都必须遵守的契约」，可延迟的细则一律下沉 references，并以**按需直达**（指明哪类任务读哪节，如「写报告前按目标类型直达 §四/§五」）代替「全部通读」。

### 3.4 实战对照

`investigate-endpoint-new` 的约束层：输出骨架（强制）+ 三层坐标配额 + 代码块白名单（只有「字面值即事实」者可贴）+ `${ENV:default}` 原样保留等实证细则 + 「疑似隐式出站，未在源码确认」的合法标注出口。渐进披露：SKILL.md 仅约百行契约（骨架 / 配额 / 自检 / 索引），schema 菜单、调查指南、范例与反例全部置于三个 references 文件按需加载。

## 四、验证层：自检清单与 self-refine 回路

### 4.1 原理

自检清单（checklist prompting）利用模型的自评能力：生成后逐条机械核对，比生成时「注意」更能拦截违规。学术界的 **Self-Refine**（迭代自精炼，生成 → 自反馈 → 修订循环）证明 LLM 能用自身反馈改进自身输出。

### 4.2 关键实践：回路出口必须显式

清单只解决「核对」，不解决「核对之后」。必须显式写明出口语义：

> 任一项不通过 → 修复对应问题后**重新逐条核对**，全过才输出；不得为过检而弱化、删改或省略事实。

没有出口语义时，模型可能核对出问题但照原样输出；还要防**反向作弊**——为过检而删掉不合格的事实（所以出口要加「不得为过检而弱化事实，事实类不合格只能修实证来源」）。

### 4.3 清单设计原则

- **机械可核对**优先：每步动词开头 ≤ 30 字这类可数的规则优于「写得清晰」这类判断题；
- 正确性与密度分开列（两类失败的修复动作不同）；
- 清单项与正文规则一一对应——清单不是新增规则，是规则的核对视图。

## 五、Eval 层：评测驱动开发（第一杠杆）

### 5.1 为什么是第一杠杆

样本、约束、验证三层都在「提高单次输出质量」，但 **skill 是会被反复修改的**——每次改规则（加一条配额、改一处措辞）都可能引入回归。没有 eval 的修改是盲改：你以为在优化，实际可能在破坏，且无人知晓。业界（Anthropic 的 skill 工程指南、各家 prompt 管理平台）一致把 eval 列为 prompt/skill 工程的基础设施。

### 5.2 最小可用 Eval 闭环

```
金标准案例（golden set）
   │  固定输入 prompt（一字不差，防输入漂移）
   ▼
无基准记忆的执行者（子代理）独立跑一遍
   │  与基准逐卡 diff
   ▼
Rubric 判分（非逐字匹配）────► 归因三分法
   │                              ├─ 规则回归 → 修规则 / 回滚
   PASS → 追加基线记录            ├─ 代码演进 → 更新基准（代码变了不是规则的错）
   FAIL → 修复后重跑               └─ 表达等价 → PASS（不追求逐字一致）
```

四个不可省略的设计点：

| 设计点 | 反模式 |
|--------|--------|
| **固定输入**：prompt 模板一字不差 | 每次措辞不同 → diff 全是噪音 |
| **防自我污染**：重跑者禁读基准（范例文件、协议本身） | 模型复述基准 → 测的是记忆力不是规则效果 |
| **rubric 判分**：按维度（事实准确 / 结构合规 / 覆盖完整）判 | 逐字 diff → 大量假阳性 |
| **归因三分法**：区分规则回归 / 代码演进 / 表达等价 | 输出不同即 FAIL → 把代码变更误判为规则回归 |

### 5.3 Eval 的双向价值

eval 不只拦截回归，还会**发现基准的缺口**：重跑报告若在某些事实上深于基准（说明基准调查有遗漏），应把新事实**回灌基准**——基准本身也在 eval 循环中变强。

### 5.4 工具生态

轻量起步用「子代理 + 固定 prompt + 人工 diff」即可；规模化后可用评测框架（promptfoo、Braintrust、LangSmith，Claude Code 生态的 plugin eval 等）做参数扫描、多版本对比与 CI 集成。工具差异在自动化程度，方法论不变。

## 六、架构层：多 Agent 信息约束

### 6.1 原理：用信息隔离防臆造

单 Agent 全流程（读码 → 成文）的固有风险：写报告时源码细节「就在上下文里」，惰性或幻觉可能直接编造一个看似合理的细节。架构层的解法是**分工 + 信息约束**：

```
调查 Agent：读源码 → 产出「事实表」（坐标、报文、配置值，禁写散文）
    │ 只传事实表
    ▼
写作 Agent：只见事实表、不见源码 → 按格式契约成文
```

写作 Agent **没有源码可看，就编造不了源码**——这是结构性防臆造，比「禁止臆造」的纪律性约束强一个量级。

### 6.2 何时值得上

成本：双 Agent 编排 + 事实表中间格式的设计维护。**仅当「实证提取 + 坐标锚定 + 编造反例」三重约束下仍有臆造时才引入**；多数 skill 用不到这一层。

### 6.3 同族实践

- **先读后写**（plan-then-execute）：禁止边读边写，调查完再成文——最轻量的流程约束；
- **工作流显式化**：把「先定位入口 → 沿调用链下行 → 识别出站」写成编号步骤，每步有产出物，防止调查漫无目的。

## 七、反馈层：human loop 与生产反馈回写

### 7.1 原理

再好的初始设计也预测不了所有失败模式。**真实使用中被人工纠正的每一次输出，都是最高价值的训练数据**——它精确定位了「现有样本/约束没拦住的失败」。业界称 production feedback loop。

### 7.2 落地形态（几乎零成本）

```
用户纠正了一次输出
   → 判断：这是新失败模式还是旧模式复发？
   → 新模式：把病理写进反例区（一条 ❌ + 正确做法）
   → 旧模式复发：说明对应约束力不足，加强该约束或给该类型补范例
```

前提是反例库被当作**活文档**维护，而非一次写成后封存。配套习惯：记录「这条反例来自哪次真实失败」，避免反例库退化为想象出的失败集。

### 7.3 Human loop 的三个位置与价值排序

human loop 不是一种质量手段，而是三种——加在哪个位置决定价值：

| 位置 | 价值 | 内容 |
|------|------|------|
| **沉淀位** | 最高 | 人工判断 → 固化为可复用资产：建基复核（人工判断固化为金标准，此后每次回归复用这一次投入）、纠正回写（7.2）、决策成文（人工裁决落为规则条文——每次介入都让下次同类情况不再需要介入） |
| **决策位** | 高 | 规则写不死的分叉：结构歧义（列出方案让用户选，skill 指令里写明触发条件）、不可逆 / 外发动作、品味类取舍（详略、措辞——无客观对错，人是唯一信号源） |
| **核对位** | 零或负 | 机械可核对维度（配额 / 格式 / 锚点 / 事实）——self-check 与 eval 比人眼快且稳；更糟的是**自动化悖论**：习惯「反正有人看着」后规则建设偷懒，人的注意力被琐事稀释后，真正的决策点反而看不住 |

两种形态的区分：**human-on-the-loop**（环上——决策点介入，机械核对委托机器）是 skill 场景的正确形态；human-in-the-loop（环内——每步经过人）摩擦成本吞掉自动化价值，仅适用于不可逆动作审批。

**一句话标准**：加 human loop 的判据不是「更安全」，而是「这次人工判断是否值得固化、是否位于机器不擅长的分叉」——**human loop 的目标是让自己退场**。

### 7.4 实操结论

| 做法 | 结论 |
|------|------|
| skill 里写「歧义 / 不可逆 / 品味 → 列方案问用户」 | ✅ 值得，触发条件写具体 |
| skill 里写「输出前请用户逐项核对」 | ❌ 核对位归机器（self-check / eval） |
| 人工介入后必问「这个判断能否沉淀为规则」 | ✅ 让下次同类情况不再需要人 |
| 把 human loop 当质量兜底而放松样本 / 约束 / eval | ❌ 最危险组合（见误区 #10） |

## 八、实战对照：investigate-endpoint 的质量演进

本项目 `investigate-endpoint-new` skill（API 执行链路调查报告）完整走过了上述六层，可作落地参照：

| 阶段 | 动作 | 对应层 |
|------|------|--------|
| 初始 | 输出骨架 + 坐标配额 + 实证提取细则 + 五类反例 + 两份开源范例 | 约束 + 样本 |
| 原则补强 | 新增「主线优先」调查原则（直接引用链 + Happy flow 优先，横切关注点必要时可放弃） | 约束 |
| 样本补型 | 补第三份范例（202 异步受理 + 轮询），反例扩到六类 | 样本 |
| 回路补全 | 自检清单加「回路出口」（不通过 → 修复 → 重检，禁为过检删事实） | 验证 |
| Eval 闭环 | 建协议（金标准 / 固定 prompt / 防自我污染 / rubric / 归因三分法），子代理 45 文件独立首跑 | Eval |
| 首跑产出 | 发现 1 处规则歧义（轮询端点是否独立 I 卡）→ 补规则；重跑 5 处事实深于基准 → 回灌基准 | Eval 双向价值 |
| 决策成文 | 规则歧义与范围决策交用户裁决（连接池归类、反例补充、通用化 share），每次裁决落为规则条文——人工零介入输出本身 | 反馈（human loop 沉淀位） |

四轮人工 review 的发现轨迹也值得参考——**每轮抓的问题类型都不同**：

1. 规则间冲突（连接池被两处归类相反）
2. 措辞歧义（「归原则三次优先」可误读为「三次优先」）
3. 事实臆造（范例中一条未实证的检测矩阵行——被 eval 首跑交叉证伪后修正）
4. 通用化残留与真实矛盾（share 化漏改一处；摘要「任何时刻 200」与关键事实「格式非法 400」矛盾）

结论：review 不是一次性动作能穷尽的；**每轮按不同视角专审**（规则一致性 → 措辞 → 事实 → 整体连贯），配合 eval 回归，才是可收敛的质量流程。

## 九、落地优先级与常见误区

### 9.1 优先级（投入产出排序）

1. **Eval 闭环**（最高）：哪怕只有一个金标准案例 + 固定 prompt + 人工 diff 也值得——它让后续所有修改有安全网；
2. **范例补型**：盘点「任务类型分布 vs 范例覆盖」，缺口类型优先补真实范例；
3. **自检回路**：给现有清单加两行出口语义（重检 + 禁为过检删事实），改动极小；
4. **human loop 落位**：反馈回写习惯 + 在 skill 里写明问询检查点（歧义 / 不可逆 / 品味类分叉），零基础设施成本；
5. **多 Agent 分离**：仅在基本盘（样本 / 约束 / 验证 / Eval）做完仍有臆造时才考虑。

### 9.2 常见误区

| # | 误区 | 后果 | 正确做法 |
|---|------|------|---------|
| 1 | 只写规则不给范例 | 边界靠模型自由发挥，方差大 | 规则解释范例，范例示范规则 |
| 2 | 负向指令当万能锁 | 无法实证时照样硬填 | 给「无法实证时怎么办」的合法出口 |
| 3 | 自检清单无回路出口 | 核对出问题但照原样输出 | 显式「不通过 → 修复 → 重检」+ 防反向作弊 |
| 4 | 无 eval 的规则修改 | 优化还是破坏无人知晓 | 改规则必回归：固定输入重跑 + diff |
| 5 | eval 追求逐字匹配 | 假阳性泛滥，很快弃用 | rubric 判分 + 归因三分法 |
| 6 | 重跑者可读基准 | 测的是复述不是规则 | 防自我污染（禁读范例与协议本身） |
| 7 | 反例库一次写成 | 预测不了真实失败模式 | 生产反馈回写，反例随失败进化 |
| 8 | 评测只看劣化 | 基准缺口永远不补 | 重跑深于基准处回灌基准 |
| 9 | 为单次输出上多 Agent | 编排成本吞掉收益 | 前四层做完仍有臆造才上 |
| 10 | 把 human loop 当质量兜底 | 四层基本盘被忽视；注意力被琐事消耗后真风险漏过（自动化悖论） | 基本盘先行；human loop 只放沉淀位与决策位（7.3） |
