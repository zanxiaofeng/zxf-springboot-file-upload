# POST /api/files/async/upload 调查报告

## Executive Summary
- 功能：multipart 文件上传安全受理：预检 → 暂存 → 返回 202 + scanId，虚拟线程后台执行「类型校验 → ClamAV → YARA → 文档威胁」四阶段扫描管道，CLEAN 入库、INFECTED 隔离、其余清理，结果经轮询端点读取
- 外部依赖：O1（文件系统 → staging 暂存）、O3（TCP → ClamAV `${CLAMAV_HOST:localhost}:${CLAMAV_PORT:3310}`）、O4（子进程 → yara CLI）、O6（文件系统 → 入库/隔离/清理）；进程内：O2、O5
- 注意：轮询结果仅存内存缓存（TTL 30 分钟），过期或重启后轮询恒返 SCANNING 占位，无 404 无终态（详见 I1）；fail-strategy=OPEN 时引擎故障文件直接入库并打标（默认 CLOSED 转轮询 ERROR）；ClamAV 客户端库无 socket 超时，挂起防护全靠应用层 60s 限时 + 熔断（详见 O3）

> 坐标相对于 `src/main/java/zxf/upload/`（配置与资源文件相对 `src/main/resources/`）。

## Inbound

### I1. 同步 HTTP → POST /api/files/async/upload（multipart 受理，202 + 轮询）

| 鉴权 | 路由 | 主坐标 |
|---|---|---|
| 无 | `POST /api/files/async/upload` | FileUploadController.java:37 |

> 受理上传：预检 → 暂存 O1 → 生成 scanId，扫描转虚拟线程后台（O2→O6），立即 202。

**关键事实**
- 请求体上限 100MB / 整请求 110MB，超限 413（与业务预检 400 分开归因）application.yml:6
- 结果查询走 `GET /api/files/async/scan/{scanId}`；结果 Caffeine 缓存 TTL 30 分钟（上限 10 万条），淘汰或重启后轮询恒返 SCANNING 占位，无 404 无法区分进行中与已丢失 AsyncScanProcessor.java:41-51
- 202 之后一切终态走轮询 body 的 status 字段（同步端点的 400/422/502 语义在此转移）

<details><summary>Request / Response / 轮询语义 / 处理逻辑 / 错误映射</summary>

**Request**
- 参数来源: multipart/form-data，part 名 `file`（唯一入参，`@RequestParam`）；无 query / header 参数
- Body（multipart 原生形态）: part `file` 携带 originalFilename（客户端可控字符串）、size、content（字节流 → O1 落盘）；无 JSON 请求体
- 入站防御: 文件名经 cleanedName 剥离目录部分（防路径混淆，反斜杠归一化后取 basename，null 兜底 "unknown"）；客户端可控字符串入日志前剥离 ISO 控制字符（防 log forging）；文件名/路径不回显响应

**Schema 校验**
- 机制: 无声明式校验（Command 无 Bean Validation 注解，参数无 @Valid）；受理预检为命令式 UploadPolicy（Checker 委托 domain 策略）
- 预检拒绝集（拒即受理 400）: size ≤ 0（空文件）/ size > 100MB / 有扩展名且不在 14 类白名单（pdf docx xlsx pptx doc xls ppt jpg png gif bmp txt csv zip，另 jpeg 别名互认）
- 流程事实: 无扩展名文件通过受理预检，由管道阶段 1（O2）按内容探测判「类型与扩展名不符」拒绝——终态走轮询 REJECTED，而非受理 400

**Response — Success**
- Status: `202 Accepted`
- Body 字段: scanId ← Executor 生成的 UUID；status 固定 SCANNING；filePath 为 null 省略（@JsonInclude(NON_NULL)）

```json
{ "scanId": "{uuid}", "status": "SCANNING", "message": "扫描进行中" }
```

**轮询语义**（异步受理形态，客户端持 scanId 轮询上述端点）
- scanId 经 UUID 正则校验（大小写十六进制），格式非法 400 VALIDATION_ERROR；任意格式合法的 scanId 恒 200，不存在 404 分支
- 进行中占位: status=SCANNING（同上 body）；终态四种: CLEAN / INFECTED / REJECTED / ERROR
- 结果保留: Caffeine expireAfterWrite=30 分钟（`zxf.virus-scan.result-retention-minutes`）+ maximumSize=100_000；缓存仅存内存，重启全部失联，淘汰/丢失后恒返占位
- CLEAN 的 message 可携带打标透传: "文件安全（macro-flagged: …）"（← O5 FLAG 策略）或 "文件安全（scan-engine-degraded）"（← O6 fail-open）；filePath ← O6 入库文件名

```json
{ "scanId": "{uuid}", "status": "CLEAN", "message": "文件安全", "filePath": "{uuid}.{ext}" }
```

- INFECTED / REJECTED / ERROR 与上同构: message 分别为 "检测到威胁: {threat}"（threat ← O3/O4/O5）、"文件被拒绝: {reason}"（reason ← O2 或预检）、"扫描引擎暂时不可用，请稍后重试"（固定安全文案）；三者 filePath 均省略

**处理逻辑**
- ① 校验空文件 / 大小 / 扩展名（UploadPolicy 预检，拒即 400）
- ② 暂存上传流到 staging 目录（调用 O1）
- ③ 生成受理凭证 scanId（UUID）
- ④ （异步：不等结果）提交虚拟线程执行管道 O2→O3→O4→O5 与处置 O6
- ⑤ 组装 202 body（scanId ← ③）返回

**错误映射表**（受理通道，HTTP 状态码承载）

| 场景 | 来源 | 对外响应 | 泄漏 |
|---|---|---|---|
| multipart 超限（file >100MB / 请求 >110MB） | 平台限制 | 413 FILE_TOO_LARGE「文件超过大小限制」 | 否 |
| 缺 file part / 非 multipart 请求 | 平台限制 | 400 FILE_REJECTED「缺少上传文件或请求格式非法」 | 否 |
| 空文件 / 超 100MB / 扩展名不在白名单 | 本地校验 | 400 FILE_REJECTED {原因文案} | 否 |
| 暂存落盘 IO 故障（O1 传播） | 下游传播 | 400 FILE_REJECTED「文件暂存失败，请稍后重试」 | 否（内部路径仅日志） |
| 未捕获异常 | 未捕获 | 500 INTERNAL_ERROR 固定文案 | 否 |

**错误映射表**（202 之后，轮询 body 的 status 承载）

| 场景 | 来源 | 对外响应 | 泄漏 |
|---|---|---|---|
| scanId 非 UUID 格式 | 本地校验 | 400 VALIDATION_ERROR | 否 |
| 未知 / 已淘汰 / 重启丢失的 scanId | — | 200 SCANNING 占位（无 404） | — |
| 管道拒绝（类型不符 / ZIP 炸弹 / 宏 BLOCK） | 管道判定 | 200 body status=REJECTED + reason | 否 |
| 检出威胁（O3 / O4 / O5 传播） | 下游传播 | 200 body status=INFECTED + threat 描述 | 否 |
| 引擎故障（fail-strategy=CLOSED，默认） | 下游传播 | 200 body status=ERROR + 固定安全文案 | 否 |

</details>

## Outbounds（管道 O2→O3→O4→O5 首个非 Passed 结论即短路；Semaphore(16) 同步/异步统一背压闸门；O2–O6 均在 @Async 虚拟线程执行）

### O1. 文件系统 → staging 暂存落盘（同步，请求线程内）

主坐标：StagingService.java:42

> 承诺把上传流完整落盘并返回暂存路径，后续扫描与处置只传该路径。

**关键事实**
- 落盘 IO 故障（磁盘满/IO 错误）对外映射 400「文件暂存失败」，而非 5xx（服务端故障被表达为业务拒绝）
- 落盘失败先删残留不完整文件再抛出；目录 `${UPLOAD_STAGING:./data/upload-staging}` 启动时创建

<details><summary>操作序列 / 失败表</summary>

**操作序列**

```text
write  {staging-path}/{uuid}.{ext}   ← I1 file part 流（Files.copy, REPLACE_EXISTING）
delete {staging-path}/{uuid}.{ext}   ← 写入失败时清理残留
```

- 参数绑定: 内容 ← I1 part `file` 的 InputStream；文件名 = 随机 UUID + 原始扩展名（小写，经 FileUtils.extension 提取）
- 写入模式: 直接覆盖写（UUID 命名保证不碰撞，无临时文件 + rename 原子性）

**失败表**

| 症状 | 处置 |
|---|---|
| 落盘 IO 失败（磁盘满 / IO 错误） | 致命-中止（I1 400） |

</details>

### O2. 进程内（Tika + commons-compress）→ MIME 探测与 ZIP 炸弹防护（管道阶段 1，无外部系统）

主坐标：FileTypeScanStage.java:43

> 承诺类型合规判定：探测真实 MIME 校验白名单与扩展名一致性，zip 加四重解压计数防护；detectedMime 流向 O5 分支路由。

**关键事实**
- 白名单 14 类 MIME（由 MIME_TO_PRIMARY_EXT 映射派生）；不符或扩展名不一致即 Rejected，短路 O3–O5（终态见 I1）
- zip 防护不信任 header 声明大小，全部实际解压计数：条目 10,000 / 单 entry 100MB / 累计 1GB / 压缩比 100:1，超限即时中断
- 损坏 zip 或声明与实际不符按引擎故障上抛（受 fail-strategy 约束，默认 fail-closed 拒绝）

<details><summary>一致性规则 / 数据流向</summary>

**MIME-扩展名一致性规则**（影响拒绝集的映射）
- 特判互认: image/jpeg ↔ jpg/jpeg；text/plain ↔ txt/csv（CSV 常被 Tika 探测为 text/plain）
- 其余按 MIME_TO_PRIMARY_EXT 主扩展名精确匹配（如 application/pdf 要求 .pdf）
- 通过 MIME 白名单的文件必有主扩展名映射，无扩展名文件必被此步拒绝

**数据流向**
- detectedMime（Tika.detect(暂存文件)）→ 管道上下文 → O5 扫描分支路由（officedocument/msword 等 → 文档分支；application/zip → 本阶段 ZIP 防护分支）

</details>

### O3. TCP → ClamAV 守护进程（clamav-client 2.1.2，INSTREAM 流式）

| 目标 | 主坐标 |
|---|---|
| `${CLAMAV_HOST:localhost}:${CLAMAV_PORT:3310}` | ClamAvScanner.java:76 |

> 承诺病毒判定：流式送检暂存文件，返回威胁描述或 null；一切引擎故障统一抛 SCAN_ENGINE_ERROR。

**关键事实**
- 客户端库无 socket 超时配置（挂起即调用线程永久阻塞），应用层虚拟线程限时 60s 兜底（`${CLAMAV_TIMEOUT_SECONDS:60}`）ClamAvScanner.java:53
- 熔断器: 计数窗口 10 次、最少 5 次起算、失败率 50% 打开、OPEN 保持 30s、半开放行 3 次 ClamAvScanner.java:62
- 超时与连接失败均计入熔断失败率，持续故障自动隔离引擎（快速失败）

<details><summary>会话与报文 / 失败表</summary>

**会话与报文**
- 协议由 clamav-client 2.1.2 封装: scan(InputStream) 将暂存文件流式送 ClamAV daemon（INSTREAM），SDK 类型不出 ClamAvScanner；超时保护为「扫描任务提交虚拟线程 + Future 限时等待」，被放弃的挂起任务阻塞成本极低，等 TCP 超时自然回收
- 响应映射: VirusFound → 威胁串 "ClamAV: {病毒名}: {命中文件}"（多病毒分号连接）；干净 → null
- 本地消费: threat 非 null → Infected 结论 → O6 隔离 + I1 轮询 message「检测到威胁: …」；null → Passed 进 O4

**失败表**

| 症状 | 处置 |
|---|---|
| 连接失败 / 协议错误 | 致命-上抛（见 I1） |
| 扫描超时 60s | 致命-上抛（计入熔断） |
| 熔断打开 | 致命-上抛（快速失败） |

</details>

### O4. 子进程 → yara CLI（自定义规则匹配；条件: yara.enabled=true，默认开）

| 命令 | 主坐标 |
|---|---|
| `${YARA_BINARY:yara}` | YaraScanner.java:45 |

> 承诺规则命中判定: 子进程扫描暂存文件，退出码非 0 即执行错误，输出非空即命中。

**关键事实**
- 命中判定非标准: yara 退出码 0 仅表执行成功，命中与否以 stdout 是否为空判断（退出码 ≠ 业务结果）
- 进程超时 60s 强杀（destroyForcibly）；stdout 读取移入独立虚拟线程防挂起，进程退出后输出排空宽限 5s
- 规则 classpath:rules/malware.yar 启动时解出到临时文件（deleteOnExit）；enabled=false 时完整跳过（不解析规则路径，规则缺失也能启动）

<details><summary>命令行 / 输出解析 / 失败表</summary>

**命令行**

```bash
${YARA_BINARY:yara} -s --fail-on-warnings {rulesTmpPath} {stagingFile}
# 3 条规则: Ransomware_Note_Indicators / Suspicious_Office_Macro / PDF_Embedded_JS_AutoExec
```

- 输入: {stagingFile} ← O1 暂存文件绝对路径；{rulesTmpPath} ← classpath 规则解出
- 环境继承: ProcessBuilder 默认全继承环境变量；错误流合并 stdout

**输出解析与退出码**
- 退出码 0 + 输出空 → 干净（null）；退出码 0 + 输出非空 → 命中，取非缩进行首列规则名去重拼接 "YARA: {规则1}, {规则2}"；退出码非 0 → 引擎错误
- 本地消费: 命中串 → Infected 结论 → O6 隔离 + I1 轮询 message

**失败表**

| 症状 | 处置 |
|---|---|
| 进程超时 60s | 致命-中止-强杀进程 |
| 退出码非 0（含 --fail-on-warnings 告警） | 致命-上抛（见 I1） |
| 输出排空超时 5s | 致命-上抛（见 I1） |
| enabled=false | 降级-跳过 |

</details>

### O5. 进程内（POI 5.5.1 / JDK ZipFile）→ 文档威胁检测（管道阶段 4；条件: 文档 MIME；无外部系统）

主坐标：DocumentThreatScanStage.java:28

> 承诺文档威胁判定与分级: 按 O2 的 detectedMime 分支浅检测 OOXML/OLE2/PDF，宏按策略放行打标或拦截。

**关键事实**
- 触发条件: detectedMime 含 officedocument / msword / ms-excel / ms-powerpoint 或为 application/pdf；非文档直通（不消耗任何扫描）
- macro-policy=FLAG 时仅宏类可放行打标（CLEAN + threat "macro-flagged: {描述}" 透传轮询 message）；默认 BLOCK 判 INFECTED 隔离；ActiveX 与 PDF 危险动作不受策略影响始终拦截（canBeFlagged 仅 MACRO）
- PDF 关键字扫描对 FlateDecode 压缩对象流无效（已知限制，深度检测由 O3/O4 兜底）

<details><summary>三分支检测 / 失败表</summary>

**三分支检测**（按 detectedMime 路由，不信任客户端扩展名）
- OOXML（docx/xlsx/pptx）: 遍历 zip 条目名——activex/ 前缀 → ACTIVE_X（优先判定，防宏 FLAG 放行绕过）；vbaproject.bin 结尾 → MACRO
- OLE2（doc/xls/ppt）: POI VBAMacroReader 提取宏模块，逐模块小写匹配 10 个可疑 token（autoopen / shell / powershell 等）命中即 MACRO；无宏或全良性 → null
- PDF: 1MB 分块 + 64B 重叠窗口扫 /javascript /openaction /launch——/Launch 单独命中即 PDF_ACTION；JavaScript 与 OpenAction 并存才判 PDF_ACTION

**失败表**

| 症状 | 处置 |
|---|---|
| 检测内部异常 | 致命-上抛（见 I1） |

</details>

### O6. 文件系统 → 处置动作（入库 / 隔离 / 清理；条件: 按 ScanStatus 查表 FileDisposition.of）

主坐标：FileScanService.java:81

> 承诺文件生命周期收口: CLEAN 入库存储区、INFECTED 隔离、其余删除暂存文件。

**关键事实**
- fail-strategy=OPEN 时引擎故障文件照常入库并打标 scan-engine-degraded（threat 透传轮询 message）；仅 SCAN_ENGINE_ERROR 可降级，业务拒绝不会被放行 FileScanService.java:117
- 隔离 move 跨文件系统失败降级 copy+delete，再失败仅记 ERROR 日志——文件滞留 staging，无重试无告警
- 入库与隔离均重命名 UUID（.quarantined 后缀 / 保留扩展名），原名与物理路径不进轮询响应（filePath 仅文件名）；隔离区权限收敛 rwx------（POSIX 生效）

<details><summary>操作序列 / 失败表</summary>

**操作序列**（背压: 入口 Semaphore(16)，许可耗尽挂起等待）

```text
copy   {staging}/{uuid}.{ext} → {base-path}/{uuid}.{ext}      ← CLEAN 入库（先入库再删暂存）
move   {staging}/{uuid}.{ext} → {quarantine}/{uuid}.quarantined ← INFECTED 隔离
delete {staging}/{uuid}.{ext}                                  ← REJECTED / ERROR 清理
```

- 参数绑定: staging 路径 ← O1；入库返回文件名 {uuid}.{ext} → I1 轮询 filePath；目录 `${UPLOAD_STORAGE:./data/upload-storage}` 与 `${UPLOAD_QUARANTINE:./data/upload-quarantine}` 启动时创建

**失败表**

| 症状 | 处置 |
|---|---|
| 隔离 move 失败（跨文件系统） | 降级-copy+delete |
| copy 后仍失败 | 忽略-记日志（滞留 staging） |
| fail-open 降级入库失败 | 致命-上抛（见 I1） |

</details>

## 补充说明
- scanId 数据主线（跨卡）: I1 生成 UUID → 202 body → AsyncScanProcessor 的 Caffeine 缓存 key（TTL 30 分钟 / 上限 100,000）→ 轮询 key；缓存纯内存，服务重启后全部 scanId 失联且轮询无任何错误信号
- 同步对照端点 `POST /api/files/sync/upload`: 同一受理结构但在请求线程内同步跑完整管道，超过 20MB（sync-max-file-size）预检 400 引导走本异步端点；两个端点共用 O1–O6、同一 Semaphore 背压与同一处置映射，差异仅在终态表达（同步抛 BusinessException → HTTP 400/422/502，异步收敛为轮询 body status）
- 管道总开关 `zxf.virus-scan.enabled=false` 时 O2–O5 全部直通（CLEAN 直接入库），受理预检与 O1/O6 仍执行
