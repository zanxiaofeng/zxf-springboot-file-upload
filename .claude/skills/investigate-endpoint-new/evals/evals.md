# 回归评测协议

本协议用于验证规则修改是否同时改善触发准确性、报告质量和调查效能。它面向 Skill 维护者与评测执行者，不属于调查报告。历史运行记录不能替代当前版本的重跑结果；未实际执行的用例只能记为 `NOT RUN`。

## 一、评测层次与出口

| 层次 | 内容 | 触发时机 | 出口 |
|---|---|---|---|
| 静态检查 | 校验器自测、三份范例校验、JSON 语法、Skill 打包验证 | 每次改动 | 所有实际执行的命令退出码为 0 |
| 触发评测 | `cases.json` 中正向与负向触发用例 | description 或触发边界变化时 | 逐案记录，正负向均达到预期；失败时调整触发描述 |
| 质量评测 | smoke 三案及 held-out 一案，with-skill／without-skill 对照 | 调查规则、报告契约或范例变化时 | 所有 with-skill 用例通过硬门禁且总分至少 85；held-out 不得豁免 |
| 效能评测 | token、耗时、读取文件数、参考文件加载量 | 与质量评测同步 | 完整记录；有旧基线时分析回归，无旧基线时只建基，不伪造提升结论 |

仅改错别字且不改语义时，可只跑静态检查，但须记录改动 diff 和理由。其余豁免不得覆盖 held-out 用例。命令因网络、权限或环境失败时记为 `BLOCKED`，不能写成 `PASS` 或 `FAIL`。

## 二、固定实验条件

1. 使用 `cases.json` 中的仓库、完整 commit、入口和固定 prompt；不得用当前 `main` 替代固定版本。
2. 每个用例使用全新上下文。with-skill 与 without-skill 采用相同模型、推理设置、工具权限、源码副本和超时预算。
3. with-skill 只加载当前 Skill；without-skill 不暴露 `SKILL.md` 或任何 Skill 资源。两组都只获得任务 prompt，不获得评分提示。
4. 为防止答案泄漏，质量评测的两组均禁止读取 `references/example-*.md`、`evals/` 和既往运行报告。with-skill 可读取主文件、调查指南、报告契约和相关协议小节。
5. 默认只做静态源码调查，不启动或调用目标服务，不请求目标下游，不修改业务源码。依赖源码或官方文档只能作为带版本的补充证据。
6. 同一案例的对照运行应尽量相邻执行。若平台不支持 token 或文件读取统计，相应字段填 `N/A`，不得估算后冒充实测。

## 三、执行步骤

### 1. 静态检查

在 Skill 根目录运行：

```bash
python scripts/test_validate_report.py
python scripts/validate_report.py references/example-crud.md references/example-distributed.md references/example-async.md
python -m json.tool evals/cases.json >/dev/null
```

打包工具的结构验证与归档完整性检查也应通过。静态检查只证明结构和语法，不证明源码事实正确。

### 2. 触发评测

向独立选择器只暴露 Skill 的 `name` 与 `description`，逐条输入 `trigger_cases` 的 prompt。记录 `expected_trigger`、`actual_trigger` 和选择理由。正向用例未触发或负向用例误触发都需保留原始结果；不能用人工强制调用掩盖选择错误。

这组小规模用例用于回归，不足以证明统计意义上的通用触发准确率。新增真实误触发或漏触发场景时，应补入 `cases.json`。

### 3. 质量与效能对照

对每个 `quality_cases` 用例分别运行：

- `with-skill`：按当前 Skill 独立调查并产出报告；
- `without-skill`：在相同环境下仅凭通用能力调查并产出报告。

报告与运行元数据保存到采用者自建的 `evals/runs/<run-id>/`，建议结构：

```text
<run-id>/
  metadata.json
  <case-id>.with-skill.md
  <case-id>.without-skill.md
  <case-id>.scorecard.json
  <case-id>.diff.md
```

`metadata.json` 至少记录：运行 ID、开始与结束时间、Skill 版本或内容哈希、目标仓库与 commit、模型与推理设置、工具与权限、原始 prompt、执行环境、运行状态和异常信息。

评分者先对照 `baseline.md` 核验 with-skill 报告，再以同一标准核验 without-skill 报告。评分依据必须回指源码；baseline 只是最低期望，不是可照抄的完整答案。两组报告均应运行静态校验器，但 without-skill 不因此被要求逐字模仿 Skill 的排版，只有采用同一报告契约进行对照评分时才把结构校验作为硬门禁。

## 四、质量评分

### 硬门禁

出现任一项即判该报告 `FAIL`，总分仅用于诊断：

- 编造或实质误述路由、字段、交互、配置、错误映射、控制流或证据；
- 漏掉目标入口的主成功路径，或漏掉会直接改变调用方结论的交互／前置限制；
- 把静态推断伪称为运行时验证，或把派生 SQL、外部默认写成直接实证；
- 关键主张的坐标不存在、指向错误版本或无法支持该主张；
- 泄露真实凭证、敏感配置值或个人数据；
- with-skill 报告未通过静态校验器。

### 百分制 rubric

| 维度 | 分值 | 满分要求 | 部分给分原则 |
|---|---:|---|---|
| 事实准确 | 25 | 所有关键事实符合固定版本，派生与不确定性标注正确 | 非关键小错每项扣 5；实质错误走硬门禁 |
| 最低覆盖 | 25 | 入口、前置限制、主链路、直接交互、控制流和伴随通道完整 | 按 baseline 清单覆盖比例给分；关键缺失走硬门禁 |
| 数据契约与映射 | 15 | 关键字段完整，来源、转换和去向可追踪，Schema 与 Body 分离 | 契约或映射缺失分别扣分；泛称不能替代真实字段 |
| 失败与错误传播 | 15 | 本地失败、下游传播、平台限制和翻译层语义正确 | 按错误通道覆盖与正确性给分；臆造映射走硬门禁 |
| 证据可验证性 | 10 | 每卡有主坐标，关键协议与数值另有证据，坐标与版本匹配 | 证据不足或只给大段实现酌情扣分 |
| 表达与边界 | 10 | 摘要独立可读，编号语义清晰，只展开直接一跳，无无价值复述 | 结构混乱、下游越界或分支被编号误导时扣分 |

with-skill 的通过条件为：硬门禁全过、总分至少 85、最低覆盖至少 20、数据映射至少 12、错误传播至少 12、证据至少 8。表达等价不应扣分。

对照分析至少报告：两组总分、硬门禁差异、漏项清单、误报清单和证据有效性差异。不能仅凭篇幅更长或卡片更多判定质量更高。

## 五、效能指标

逐案记录以下实测值，并同时保留 with-skill 与 without-skill：

- 输入、输出和总 token；无法拆分时记录平台实际提供的口径；
- 端到端耗时与纯模型耗时（若可得）；
- 唯一项目源码文件读取数、重复读取次数；
- Skill 参考文件读取数及总字节数；
- 工具调用次数、调查期间产生的中间台账大小（若可得）；
- 首次产出即通过静态校验的比例。

首次执行只建立效能基线。后续同环境对比时，若总 token 或耗时上升超过 15%，必须结合质量增益说明取舍；若质量无提升且效能变差，应简化规则或按需加载路径。不得为降低 token 而删除最低覆盖、负面事实或关键证据。

## 六、diff 归因与发布决定

- **规则回归**：固定源码下，新报告较当前基线出现误报、漏项或证据退化；修复后重跑失败用例及至少一个相邻用例。
- **基线错误**：回指固定源码证明 baseline 有误；修正 baseline 并记录证据，不得为迎合旧答案判新报告失败。
- **输入漂移**：commit、prompt、模型或权限变化导致不可比；补齐条件后重跑，不归因于 Skill。
- **表达等价**：事实、覆盖和可验证性相同，仅措辞不同；不判回归。

发布前必须保存真实运行产物与评分卡。没有 agent 对照运行结果时，只能声明静态检查通过，不能声明质量或效能回归通过。
